==============================
New Worklet Types
==============================

.. index::
   single: worklet types; creating new

The basic building block for an algorithm in |Viskores| is the worklet.
:chapref:`worklet-types:Worklet Types` describes the different worklet types
provided by |Viskores| and how to use them to create algorithms. However, it is
entirely possible that this set of worklet types does not directly cover what
is needed to implement a particular algorithm. One way around this problem is
to use some of the numerous back doors provided by |Viskores| to provide less
restricted access in the execution environment, such as using whole arrays for
random access.

However, you may encounter a particular pattern of execution that you find
useful for implementing several algorithms. If so, it can be worthwhile to
create a new worklet type that directly supports such a pattern. Creating a new
worklet type can provide two key advantages. First, it makes implementing
algorithms of this nature easier, which saves developer time. Second, it can
make the implementation of such algorithms safer. By encapsulating the
management of structures and regulating data access, users of the worklet type
can be more assured of correct behavior.

This chapter documents the process for creating new worklet types. The
operation of a worklet requires the coordination of several different object
types such as dispatchers, argument handlers, and thread indices. This chapter
provides examples of all these required components. To tie all these features
together, we start with a motivating example for an implementation of a custom
worklet type. The chapter then discusses the individual components of the
worklet, which in the end come together for the worklet type that is then
demonstrated.

------------------------------
Motivating Example
------------------------------

For our motivation to create a new worklet type, let us consider the use case
of building fractals. Fractals are generally not a primary concern of
visualization libraries like |Viskores|, but building a fractal (or
approximations of fractals) has similarities to the computational geometry
problems in scientific visualization. In particular, we consider the class of
fractals generated by replacing each line in a shape with some collection of
lines. These types of fractals are interesting because, among other reasons,
the right parameters result in a shape that has infinite length confined to a
finite area.

A simple but well-known example of a line fractal is the
:index:`Koch Snowflake`. The Koch Snowflake starts as a line or triangle that
gets replaced with the curve shown in :numref:`fig:koch-shape`.

.. figure:: ../../data/users-guide/images/Koch1.png
   :align: center
   :width: 45%
   :name: fig:koch-shape

   Basic shape for the Koch Snowflake.

The fractal is formed by iteratively replacing the curve's lines with this basic shape.
:numref:`fig:koch-iteration-2` shows the second iteration and :numref:`fig:koch-iteration-5` shows it after several subsequent iterations that create a "fuzzy" curve.
The curve is confined to a limited area regardless of how many iterations are performed, but the length of the curve approaches infinity as the number of iterations
approaches infinity.

.. figure:: ../../data/users-guide/images/Koch2.png
   :align: center
   :width: 45%
   :name: fig:koch-iteration-2

   The Koch Snowflake after the second iteration.

.. figure:: ../../data/users-guide/images/Koch5.png
   :align: center
   :width: 45%
   :name: fig:koch-iteration-5

   The Koch Snowflake after several more iterations.

In our finite world we want to estimate the curve of the Koch Snowflake by
performing a finite number of iterations. This is similar to a
:index:`Lindenmayer system` but with less formality. The size of the curve grows
quickly, and in practice it takes few iterations to make close approximations.

.. didyouknow::

   The Koch Snowflake is just one example of many line fractals we can make
   with this recursive line substitution, which is why it is fruitful to
   create a worklet type to implement such fractals. We use the Koch Snowflake
   to set up the example here. :secref:`new-worklet-types:Using the Worklet`
   provides several more examples.

To implement line fractals of this nature, we want to define the lines of the
base shape in terms of parametric coordinates and then transform the
coordinates to align with a line segment. For example, the Koch Snowflake base
shape could be defined with the parametric coordinates shown in
:numref:`fig:koch-parametric`.

.. figure:: ../../data/users-guide/images/KochParametric.png
   :align: center
   :width: 55%
   :name: fig:koch-parametric

   Parametric coordinates for the Koch Snowflake shape.

Given these parametric coordinates, for each line we define an axis with the
main axis along the line segment and the secondary axis perpendicular to it.
Given this definition, we can perform each fractal iteration by applying this
transform for each line segment as shown in :numref:`fig:koch-apply`.

.. figure:: ../../data/users-guide/images/KochApply.png
   :align: center
   :width: 60%
   :name: fig:koch-apply

   Applying the line fractal transform for the Koch Snowflake.

To implement the application of the line fractal demonstrated in :ref:`fig:koch-apply`, let us define a class named ``LineFractalTransform`` that takes as its constructor the coordinates of the two ends of the original line.
As its operator, ``LineFractalTransform`` takes a point in parametric space and returns the coordinates in world space with respect to the original line segment.
We define this class in the :cpp:any:`viskores::exec` namespace because the intended use case is by worklets of the type we are making.
A definition follows.

------------------------------
Thread Indices
------------------------------

.. index::
   single: thread indices

The first internal support class for implementing a worklet type is a class
that manages indices for a thread. As the name implies, the thread-indices
class holds a reference to an index identifying work to be done by the current
thread. This includes indices to the current input element and the current
output element. The thread-indices object can also hold other information
(which may not strictly be index data) about the input and output data. For
example, the thread-indices object for topology maps, named
:cpp:class:`viskores::exec::arg::ThreadIndicesTopologyMap`, maintains cell
shape and connection indices for the current input object.

As discussed briefly in :secref:`worklet-arguments:Fetch`, a thread-indices
object is passed to the methods of :cpp:class:`viskores::exec::arg::Fetch` to
retrieve data from the execution object. The thread-indices object serves two
important functions for ``Fetch``. The first is to cache information about the
current thread that is likely to be used by multiple objects retrieving
information. For example, in a point-to-cell topology map, data from point
fields must be retrieved by looking up indices in the topology connections. It
is more efficient to retrieve the topology connections once and store them in
the thread indices than it is to look them up independently for each field.

The second function of thread indices is to make it easier to find information
about the input domain when fetching data. Once again, getting point data in a
point-to-cell topology map requires looking up connectivity information in the
input domain. However, the ``Fetch`` object for the point field does not have
direct access to the data for the input domain. Instead, it gets this
information from the thread indices.

All worklet classes have a method named ``GetThreadIndices`` that constructs a
thread-indices object for a given thread. ``GetThreadIndices`` is called with
five parameters: a unique index for the thread (that is, the worklet instance),
an array portal that maps output indices to input indices (which might not be
one-to-one if a scatter is being used), an array portal that gives the visit
index for each output index, an array portal that maps each unique thread index
to the output index for that thread, and the execution object for the input
domain.

.. doxygenfunction:: viskores::worklet::internal::WorkletBase::GetThreadIndices(const viskores::Id &threadIndex, const OutToInArrayType &outToIn, const VisitArrayType &visit, const ThreadToOutArrayType &threadToOut, const InputDomainType&) const

.. doxygenfunction:: viskores::worklet::internal::WorkletBase::GetThreadIndices(viskores::Id threadIndex1D, const viskores::Id3 &threadIndex3D, const OutToInArrayType &outToIn, const VisitArrayType &visit, const ThreadToOutArrayType &threadToOut, const InputDomainType&) const

The base worklet implementation provides an implementation of :func:`viskores::worklet::internal::WorkletBase::GetThreadIndices` that creates a :cpp:class:`viskores::exec::arg::ThreadIndicesBasic` object (or :cpp:class:`viskores::exec::arg::ThreadIndicesBasic3D` for 3D indices).
This provides the minimum information required in a thread-indices object, but non-trivial worklet types are likely to need to provide their own thread-indices type. The following example shows the implementation of ``GetThreadIndices`` that we will use in our worklet-type superclass, which is discussed in more detail in :secref:`new-worklet-types:Worklet Superclass`.

As we can see in the preceding example, our new worklet type needs a custom
thread-indices class. Specifically, we want the thread-indices class to manage
the coordinate information of the input line segment.

.. didyouknow::

   The implementation of a thread-indices object demonstrated here stores
   point-coordinate information in addition to actual indices. It is acceptable
   for a thread-indices object to store data that are not strictly indices. That
   said, the object should only load data (index or not) that are almost certain
   to be used by any worklet implementation. The thread-indices object is
   created before any worklet operator is called. If it loads data that is never
   used by a worklet, that is a waste.

An implementation of a thread-indices object usually derives from
:cpp:class:`viskores::exec::arg::ThreadIndicesBasic` (or some other existing
thread-indices class) and adds information specific to a particular worklet
type.

------------------------------
Signature Tags
------------------------------

It is common for a new worklet type to be associated with new types of data.
Thus, implementing new worklet types commonly involves defining custom tags
for ``ControlSignature`` and ``ExecutionSignature``. This in turn typically
requires creating custom :cpp:struct:`viskores::cont::arg::TypeCheck`,
:cpp:struct:`viskores::cont::arg::Transport`, and
:cpp:struct:`viskores::exec::arg::Fetch` classes.

:chapref:`worklet-arguments:Worklet Arguments` describes in detail the process
of defining new worklet arguments and the associated code to manage data from
a :cpp:class:`viskores::cont::Invoker` argument to the data passed to the
worklet operator. Rather than repeat that discussion, readers should review
that chapter for details on how custom arguments are defined for a new worklet
type. In particular, we use the examples that define a custom
``TypeCheck``, ``Transport``, and ``Fetch`` to implement an argument
representing 2D line segments (our input domain). All these examples culminate
in the definition of a ``ControlSignature`` tag in our worklet superclass.

.. load-example:: WorkletLineFractalInputDomainTag
   :file: GuideExampleFractalWorklets.cxx
   :caption: Custom ``ControlSignature`` tag for the input domain of our example worklet type.

As you have worked with different existing worklet types, you have likely
noticed that different types have special ``ExecutionSignature`` tags that
point to information in the input domain. For example, a point-to-cell topology
map has special tags for getting the input cell shape and the indices of all
points incident on the current input cell. We described at the beginning of
the chapter that we wanted our worklet type to provide implementations with a
``LineFractalTransform`` object (see :numref:`ex:LineFractalTransform`), so it
makes sense to define our own custom ``ExecutionSignature`` tag to provide this
object.

:chapref:`worklet-arguments:Worklet Arguments` gives an example of a custom
``ExecutionSignature`` tag that modifies what information is fetched from an
argument. However, tags that only pull data from the input domain behave a
little differently because they only get information from the thread-indices
object and ignore the associated data object. This is done by providing a
partial specialization of :cpp:struct:`viskores::exec::arg::Fetch` that
specializes on the aspect tag but not on the fetch tag.

.. load-example:: InputDomainFetch
   :file: GuideExampleFractalWorklets.cxx
   :caption: A ``Fetch`` for an aspect that does not depend on any control argument.

The definition of an associated ``ExecutionSignature`` tag simply has to use
the defined aspect as its ``AspectTag``. The tag also has to define an ``INDEX``
member (which is required of all ``ExecutionSignature`` tags). This is
problematic because this execution argument does not depend on any particular
control argument. Thus, it is customary to simply set ``INDEX`` to 1. There is
guaranteed to be at least one ``ControlSignature`` argument for any worklet
implementation. Thus, the first argument is sure to exist and can then be
ignored.

.. load-example:: WorkletLineFractalTransformTag
   :file: GuideExampleFractalWorklets.cxx
   :caption: Custom ``ExecutionSignature`` tag that relies only on input-domain information in the thread indices.

So far we have discussed how to get input line segments into our worklet. We
also need a ``ControlSignature`` tag to represent the output line segments
created by instances of our worklet. The motivating example has each worklet
outputting a fixed number (greater than 1) of line segments for each input line
segment. To manage this, we define another ``ControlSignature`` tag that
outputs these line segments as two :cpp:type:`viskores::Vec`-2 coordinates.
This is defined as a ``Vec`` of ``Vec``-2 objects. The tag takes the number of
line segments as a template argument.

------------------------------
Worklet Superclass
------------------------------

The penultimate step in defining a new worklet type is to define a class that
will serve as the superclass of all implementations of worklets of this type.
This class must inherit from
:cpp:class:`viskores::worklet::internal::WorkletBase`. By convention the
worklet superclass is placed in the :cpp:any:`viskores::worklet` namespace and
its name starts with ``Worklet``.

.. doxygenclass:: viskores::worklet::internal::WorkletBase

Within the worklet superclass we define the signature tags ,as discussed in
:secref:`new-worklet-types:Signature Tags`, and the ``GetThreadIndices`` methods,
as discussed in :secref:`new-worklet-types:Thread Indices`. The worklet
superclass can also override other default behavior of ``WorkletBase`` (such
as a special scatter) and provide other items particularly useful to its
subclasses (such as commonly used tags). It must also declare a
``Dispatcher`` template that points to a *dispatcher* object used
to invoke the worklet. The dispatcher is created in
:secref:`new-worklet-types:Dispatcher`.

.. load-example:: WorkletLineFractal
   :file: GuideExampleFractalWorklets.cxx
   :caption: Superclass for a new type of worklet.

.. commonerrors::

   Be wary of creating worklet superclasses that are templated. The C++
   compiler rules for superclass templates that are only partially specialized
   are non-intuitive. If a subclass does not fully resolve the template,
   features of the superclass such as signature tags will have to be qualified
   with ``typename`` keywords, which reduces the usability of the class.

------------------------------
Dispatcher
------------------------------

.. index::
   single: dispatcher
   single: dispatcher; creating new
   single: invoke

Worklets are instantiated in the control environment and run in the execution
environment. This means that the control environment must have a means to
*invoke* worklets that start running in the execution environment. This is
ostensibly done by the :cpp:class:`viskores::cont::Invoker` object, but
``Invoker`` does this through a *dispatcher* object.

A dispatcher object is an object in the control environment that has an
instance of a worklet and can invoke that worklet with a set of arguments.
There are multiple types of dispatcher objects, each corresponding to a type
of worklet object. All dispatcher objects have at least one template parameter:
the worklet class being invoked, which is always the first argument. All
dispatcher objects must be constructed with an instance of the worklet they
are to invoke.

All dispatcher classes have a method named ``Invoke`` that launches the worklet
in the execution environment. The arguments to
:cpp:func:`viskores::worklet::internal::DispatcherBase::Invoke` must match those
expected by the worklet, which is specified by a *control signature*.

The following dispatchers are defined in |Viskores|. These classes correspond
to the worklet types specified in :chapref:`worklet-types:Worklet Types`.

.. doxygenclass:: viskores::worklet::DispatcherMapField

.. doxygenclass:: viskores::worklet::DispatcherMapTopology

.. doxygenclass:: viskores::worklet::DispatcherPointNeighborhood

.. doxygenclass:: viskores::worklet::DispatcherReduceByKey

The final element required for a new worklet type is an associated dispatcher
class for invoking the worklet.

:cpp:class:`viskores::worklet::internal::DispatcherBase`. ``DispatcherBase``

   :members:
   :protected-members:

.. didyouknow::

   The convention of having a subclass be templated on the derived class's type
   is known as the Curiously Recurring Template Pattern (CRTP). In the case of
   ``DispatcherBase``, |Viskores| uses this CRTP behavior to allow the general
   implementation of ``Invoke`` to run ``DoInvoke`` in the subclass, which, as
   we see in a moment, is itself templated.

.. load-example:: DispatcherSuperclass
   :file: GuideExampleFractalWorklets.cxx
   :caption: Subclassing ``DispatcherBase``.

The dispatcher should have two constructors. The first constructor takes a
worklet and a scatter. Both arguments should have a default value that is a new
object created with its default constructor. It is good practice to put a
warning on this constructor explaining that a compile error there probably
means the worklet or scatter does not have a default constructor and one needs
to be provided. The second constructor just takes a scatter.

.. load-example:: DispatcherConstructor
   :file: GuideExampleFractalWorklets.cxx
   :caption: Typical constructors for a dispatcher.

Finally, the dispatcher must implement a const method named ``DoInvoke``. The
method should take a single argument. The argument will be an object of type
:struct:`viskores::internal::Invocation`, although it is usually more
convenient to express the argument type as a single template parameter. The
``Invocation`` template could contain several data items, so it is best to pass this
argument as a constant reference.

.. load-example:: DispatcherDoInvokePrototype
   :file: GuideExampleFractalWorklets.cxx
   :caption: Declaration of a dispatcher's ``DoInvoke`` method.

.. index::
   single: invocation object
   single: dispatcher; invocation object

.. doxygenstruct:: viskores::internal::Invocation
   :members:

:struct:`viskores::internal::Invocation` is an object that encapsulates the
state and data relevant to the invoke. It contains multiple types and data
items. For brevity, only the ones most likely to be used in a ``DoInvoke``
method are documented here. We discuss these briefly before returning to the
implementation of ``DoInvoke``.

The data member :var:`viskores::internal::Invocation::Parameters` contains the
data passed to the dispatcher's ``Invoke`` method (with some possible
transformations applied). ``Parameters`` is stored in a
:class:`viskores::internal::FunctionInterface` template object.
(:chapref:`function-interface:Function Interface Objects` describes
``FunctionInterface``.) The specific type of ``Parameters`` is defined with
:type:`viskores::internal::Invocation::ParameterInterface` type in the
``Invocation`` object.

The ``Invocation`` object also contains the
:type:`viskores::internal::Invocation::ControlInterface` and
:type:`viskores::internal::Invocation::ExecutionInterface` types, which are
:class:`viskores::internal::FunctionInterface` classes built from the worklet's
``ControlSignature`` and ``ExecutionSignature``. These ``FunctionInterface``
classes provide a simple mechanism for introspecting the arguments of the
worklet's signatures.

All worklets must also define an input-domain index, which points to one of the
``ControlSignature``/``Invocation`` arguments. This number is captured in the
``Invocation`` object in a field named
:var:`viskores::internal::Invocation::InputDomainIndex`. For convenience,
``Invocation`` also has the type
:type:`viskores::internal::Invocation::InputDomainTag` set to the same type as
the ``ControlSignature`` argument corresponding to the input domain. Likewise,
``Invocation`` has the type
:type:`viskores::internal::Invocation::InputDomainType` set to the same type as
the (transformed) input-domain argument to ``Invoke``. ``Invocation`` also has a
method named :func:`viskores::internal::Invocation::GetInputDomain` that returns
the input-domain object passed to ``Invoke``.

Getting back to the dispatcher implementation, ``DoInvoke`` should first verify
that the ``ControlSignature`` argument associated with the input domain is of
the expected type. This can be done by comparing
:type:`viskores::internal::Invocation::InputDomainTag` with the expected
signature tag using a tool like ``std::is_same``. This step is not strictly
necessary, but it is invaluable to users diagnosing issues with the dispatcher.
It does not hurt to also check that the ``Invoke`` argument for the input domain
is the expected type (by checking
:type:`viskores::internal::Invocation::InputDomainType`). It is additionally
helpful to have a descriptive comment near these checks.

.. load-example:: CheckInputDomainType
   :file: GuideExampleFractalWorklets.cxx
   :caption: Checking the input-domain tag and type.

Next, ``DoInvoke`` must determine the number of elements in the input domain.
When the default identity scatter is used, the input-domain size corresponds to
the number of instances in which the worklet is executed. Other scatters
transform the input-domain size to an output-domain size, which determines the
number of instances. The input-domain size is generally determined by using
:func:`viskores::internal::Invocation::GetInputDomain` and querying the
input-domain argument. In our motivating example, the input domain is an
:cpp:class:`viskores::cont::ArrayHandle`, and its size is half the size of the
array because array entries are paired into line segments.

The final thing ``DoInvoke`` does is call
:func:`viskores::worklet::internal::DispatcherBase::BasicInvoke` on its
superclass. :func:`viskores::worklet::internal::DispatcherBase::BasicInvoke`
does the complicated work of transferring arguments, scheduling the parallel
job, and calling the worklet's operator.

.. load-example:: CallBasicInvoke
   :file: GuideExampleFractalWorklets.cxx
   :caption: Calling ``BasicInvoke`` from a dispatcher's ``DoInvoke``.

Using the Worklet
------------------------------

Now that we have our full implementation of a worklet type that generates line
fractals, let us have some fun with it. The beginning of this chapter shows an
implementation of the Koch Snowflake. The remainder of this chapter
demonstrates other fractals that are easily implemented with our worklet type.

Tree Fractal
==============================

Another type of fractal we can make is a tree fractal. We will make a fractal
similar to a Pythagoras tree except using lines instead of squares. Our fractal
starts with a vertical line that is replaced with the off-center "Y" shape
shown in :numref:`fig:tree-fractal`. Iterative replacement using this "Y" shape
produces a bushy tree shape.

.. list-table:: The tree fractal replaces each line with the "Y" shape (left), grows branches at the end in one iteration (middle), and branches into a bushy shape after several iterations (right).
   :class: borderless
   :name: fig:tree-fractal
   :width: 100%

   * - .. image:: ../../data/users-guide/images/Tree01.png
          :width: 100%
     - .. image:: ../../data/users-guide/images/Tree02.png
          :width: 100%
     - .. image:: ../../data/users-guide/images/Tree08.png
          :width: 100%

One complication of implementing this tree fractal is that we really only want
to apply the "Y" shape to the "leaves" of the tree. For example, once we apply
the "Y" to the trunk, we do not want to apply it to the trunk again. If we did,
we would create duplicates of the first layer of branches.

We can implement this feature in our worklet by using a count scatter. Worklet
scatters are described in :secref:`worklet-in-out:Scatter`. Instead of
directing the fractal worklet to generate 3 output line segments for every
input line segment, we tell it to generate just 1 output line segment. We then
use a counting scatter to generate 3 line segments for the leaves and 1 line
segment for all other segments. The count array for the initial iteration is
initialized to a single 3. Each iteration then creates the count array for the
next iteration by writing a 1 for the base line segment and a 3 for the other
two line segments.

Dragon Fractal
==============================

.. index::
   single: dragon fractal
   single: Heighway dragon
   single: Harter-Heighway dragon
   single: Jurassic Park dragon

The next fractal we implement is known as the dragon fractal. The dragon
fractal is also sometimes known as the Heighway dragon or Harter-Heighway
dragon after creators John Heighway, Bruce Banks, and William Harter. It is
also sometimes colloquially referred to as the Jurassic Park dragon because
the fractal was prominently featured in the *Jurassic Park* novel by Michael
Crichton.

The basic building block is simple. Each line segment is replaced by two line
segments bent at 90 degrees and attached to the original segment's endpoints,
as shown in :numref:`fig:dragon-first-4`. By the fourth iteration a more
complicated pattern starts to emerge. :numref:`fig:dragon-12` shows the twelfth
iteration and demonstrates a repeating spiral.

     - .. image:: ../../data/users-guide/images/Dragon03.png
          :width: 100%
     - .. image:: ../../data/users-guide/images/Dragon04.png
          :width: 100%

What makes the dragon fractal different from the Koch Snowflake and similar
fractals like the quadratic curves is that the direction of the shape flips
from one side to the other. In the second image of
:numref:`fig:dragon-first-4`, the first bend is under its associated line
segment whereas the second is above its line segment. The easiest way for us
to control the bend is to alternate the direction of the line segments. In
:numref:`fig:dragon-first-4`, each line segment has an arrowhead indicating the
orientation of the first and second points, with the arrowhead at the second
point. The shape is defined such that the first point of both line segments
meet at the right angle. With the shape defined this way, each iteration is
applied to put the bend to the left of the segment with respect to an observer
at the first point looking at the second point.

   :align: center
   :width: 90%
   :name: fig:dragon-12

   The dragon fractal after 12 iterations.

Other than reversing the direction of half the line segments, the
implementation of the dragon fractal is nearly identical to the Koch
Snowflake.

Hilbert Curve
==============================

.. index::
   single: Hilbert curve

For our final example we look at using our fractal worklet to construct a
space-filling curve. A space-filling curve is a type of fractal that defines a
curve that, when iterated to its infinite length, completely fills a space.
Space-filling curves have several practical uses because they allow you to
order points in a 2-dimensional or higher-dimensional space in a 1-dimensional
array such that points close in the higher-dimensional space are usually close
in the 1-dimensional ordering. For this fractal we generate the well-known 2D
Hilbert curve.

The 2D Hilbert curve fills a rectangular region in space. Our implementation
fills a unit square in the [0, 1] range, but a simple scaling can generalize it
to any rectangle. Without loss of generality, we say that the curve starts in
the lower-left corner of the region and ends in the lower-right corner. The
Hilbert curve starts by snaking around the lower-left corner, then into the
upper-left, followed by the upper-right, and then the lower-right. The curve is
typically generated by recursively dividing and orienting these quadrants.

To generate the Hilbert curve in our worklet system, we define our line
segments as the connection from the lower left (entrance) of the region to the
lower right (exit) of the region. Fractal generation breaks this line into a
4-segment curve that moves up, then right, then back down.
:numref:`fig:hilbert` demonstrates the Hilbert curve. Readers familiar with the
Hilbert curve might notice that the shape is a bit different from other
representations. Where many derivations derive the Hilbert curve by connecting
the centers of oriented boxes, our derivation uses a line segment along one
edge of these boxes. The result is a more asymmetrical shape in early
iterations, but the two approaches are equivalent as the iterations approach
infinity.

Like the dragon fractal, the Hilbert curve needs to flip the shape in different
directions. For example, the first iteration, shown at left in
:numref:`fig:hilbert`, is drawn to the "left" of the initial line along the
horizontal axis. The next iteration, the second image, is created by drawing
the shape to the "right" of the vertical line segments but to the left of the
horizontal segments.

:secref:`new-worklet-types:Dragon Fractal` solved this problem for the dragon
fractal by flipping the direction of some line segments. Such an approach
would work for the Hilbert curve, but it results in line segments being listed
out of order and with inconsistent directions with respect to the curve. For
the dragon fractal, the order and orientation of line segments is of little
consequence. But for many applications of a space-filling curve, distance
along the curve is the whole point, so we want the order of the line segments
to be consistent with the curve.

To support this flipped shape while preserving line-segment order, we use a
data field attached to the line segments. That is, each line segment has a
value representing which way to draw the shape. If the field value is set to 1
(represented by the blue line segments in :numref:`fig:hilbert`), then the
shape is drawn to the "left." If the field value is set to -1 (represented by
the red line segments), then the shape is inverted and drawn to the "right."
This field is passed in and out of the worklet using the ``FieldIn`` and
``FieldOut`` tags.
